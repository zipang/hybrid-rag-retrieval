## Context & Goal

Qdrant `1.20.0` is published. The project pins `1.19.1` in the development
environment, in the local documentation mirror, and in the NixOS deployment
memo.

The development environment has three problems today:

- `scripts/init.sh` defaults to `QDRANT_VERSION=latest`, so an installation
  picks whatever release is current on the day it runs, with no trace;
- the tarball download is not verified;
- the local mirror `docs/Qdrant - 1.19.1/` is the only documentation that agents
  may read, so the project cannot use the new release before the mirror moves.

The goal is a reproducible development setup on `1.20.0`, a verified in-place
upgrade of the existing 236-point local collection, and a documented record of
every measured behavior that changed.

This ticket does **not** touch the NixOS server. The server stays pinned to
`1.19.1` until a separate ticket moves it.

### 2. Upgrade rules, documented

The upgrade rules page states:

> If you are several versions behind, multiple updates might be required to
> reach the latest version. When upgrading Qdrant, upgrade to the latest patch
> version of each intermediate minor version first.

and:

> A Qdrant node with version 1.17 will be compatible with a node with version
> 1.16, but not with a node with version 1.15. If you run a single node
> cluster, you also can not skip versions to ensure that all data migrations are
> properly applied.

Source: <https://qdrant.tech/documentation/upgrades/>, read on 2026-11-12.

`1.19` to `1.20` is one consecutive minor step, so the rule allows the direct
move.

The FAQ states:

> We do not support downgrading a cluster on any of our products. If you deploy
> a newer version of Qdrant, your data is automatically migrated to the newer
> storage format. This migration is not reversible.

Source: <https://qdrant.tech/documentation/faq/qdrant-fundamentals/>, read on
2026-11-12. The local copy is
`docs/Qdrant - 1.19.1/documentation/faq/qdrant-fundamentals/index.md`.

Consequences that the ticket enforces:

1. The first start of `1.20.0` is irreversible for the storage it opens.
   Therefore the first start opens a **copy** of `qdrant/storage`, never the
   original.
2. `qdrant/storage` is backed up before the real binary is replaced, and the
   backup stays until the CEO/PM validates the ticket.
3. The local server is a single node, so the upgrade includes downtime. That is
   acceptable for a development machine.

### 4. Baseline snapshot

A baseline is a JSON document that records what the running server returns for a
fixed set of queries. Comparing the baseline of `1.19.1` with the baseline of
`1.20.0` proves that the data survived and that the exact scores did not drift.

```ts
/** One captured state of the live collection. */
export type BaselineSnapshot = {
  /** Version reported by `GET /`. */
  version: string;
  /** Collection name. */
  collection: string;
  /** ISO-8601 capture time. Ignored by the comparison. */
  capturedAt: string;
  /** Point count reported by the collection info endpoint. */
  pointsCount: number;
  /** Query texts, in capture order. */
  queries: string[];
  /** Exact dense result per query, in capture order. */
  dense: IndexScore[][];
  /** Exact sparse BM25 result per query, in capture order. */
  sparse: IndexScore[][];
  /** Identifier of the hybrid result per query, best first. */
  hybrid: Array<Array<number | string>>;
};

/** Findings of one baseline comparison. */
export type BaselineDiff = {
  /** Differences that prove data loss or score drift. */
  blockers: string[];
  /** Differences that an upgrade may cause, and that a human must read. */
  warnings: string[];
};

/** Compare two baselines of the same collection. */
export const compareBaselines = (
  before: BaselineSnapshot,
  after: BaselineSnapshot
): BaselineDiff;
```

Comparison rules:

- `capturedAt` is ignored.
- A different `version` is a **warning** that names both versions, because the
  upgrade expects it.
- A different `collection` is a **blocker**.
- A different `pointsCount` is a **blocker**.
- A different number of queries, or a different query text at the same position,
  is a **blocker**: the comparison must not silently compare different work.
- Dense scores are compared **by identifier**, not by array position. A missing
  identifier is a **blocker**. A common identifier whose score differs by more
  than `1e-6` in absolute value is a **blocker**.
- Sparse scores use the same rule as dense scores.
- Hybrid results are compared as ordered identifier lists. A different list is a
  **warning** that names the query and the number of common identifiers, because
  HNSW search is approximate and the level assignment changed.
- Findings are sorted: blockers first by query index, then warnings.

### 5. Baseline CLI

```text
bun run scripts/qdrant-baseline.ts capture --collection slogans --out <file>
bun run scripts/qdrant-baseline.ts compare --before <file> --after <file>
```

- `capture` reads `QDRANT_URL`, creates the client from the dataset
  configuration that owns the collection, scrolls every identifier, and writes
  the snapshot as pretty JSON. It prints the path and the version.
- `compare` reads two snapshots, prints the diff as pretty JSON, and exits `1`
  when `blockers` is not empty, `0` otherwise.
- An unknown subcommand, a missing flag, or an unreadable file exits `2` with a
  message.
- The query set is the three queries of `scripts/smoke-retrieval.ts`. Duplicate
  code is acceptable here: the smoke script prints, the baseline records.
- The embedder is the configured one, built from the environment, because the
  dense query vector must match the stored vectors.
- The script never writes to the collection.

### 6. Reproducible installation

`scripts/init.sh` changes:

```sh
QDRANT_VERSION="${QDRANT_VERSION:-1.20.0}"
QDRANT_SHA256="${QDRANT_SHA256:-2361f3df0dedfef31f5444f9f15bd15d6b4a6cba6ad952daecc5fbe3867c5ee6}"
```

- The pinned version and the pinned hash move together. A future upgrade
  changes both lines in one place.
- After the download and before extraction, the script computes the SHA-256 of
  the tarball. A mismatch removes the file, exits `1`, and prints the expected
  and the actual hash.
- `QDRANT_SHA256=` (empty) disables the check. The help text says so, because a
  user who sets `QDRANT_VERSION=latest` must also clear the hash.
- `--force` still re-downloads. `--skip-qdrant` still skips the step.
- The Web UI stays on `QDRANT_WEB_UI_VERSION=latest`. Its version is independent
  of the server version, and this ticket does not touch it.

### 8. In-place verification procedure

1. Capture the `1.19.1` baseline while the 1.19.1 server still runs on 6333.
2. Stop the server (`bun run qdrant:stop`).
3. Copy `qdrant/storage` to `qdrant/storage.bak-1.19.1`. This is the rollback
   material, and it is not optional.
4. Copy `qdrant/storage` to a scratch directory with a copy of
   `qdrant/config/config.yaml`, start the new binary there with
   `QDRANT__SERVICE__HTTP_PORT=6433`, and capture the first `1.20.0` baseline on
   the copy.
5. Compare the two baselines. Blockers mean the upgrade is refused.
6. When the comparison is clean, install the new binary with
   `bun run init --force --skip-model`, start the server on 6333, capture the
   baseline again, and compare it with the 1.19.1 baseline.
7. Keep `qdrant/storage.bak-1.19.1` until the CEO/PM validates the ticket.

The scratch start proves that the storage migration runs. The real start proves
that the installed setup works on the normal port.

### 9. Re-checks after the upgrade

Re-run the five checks of
`memos/qdrant-multivector-behavior.md`, section "Checks to repeat after an
upgrade", against `1.20.0`. Expected results from 1.19.1:

1. `PUT /collections/{name}/vectors/{vector}` with `multivector_config` adds the
   definition, and the collection info reports `max_sim`.
2. An update-vectors request with one key only keeps the other vectors and the
   payload unchanged.
3. A two-row matrix against a record with the same two rows scores `2.0`.
4. A batch vector delete that contains an absent identifier still clears the
   present identifiers.
5. `4096` rows of `256` dimensions are refused.

Also re-run the two quirks of `memos/syntax-trees.md`:

1. A two-row matrix whose rows are unit basis vectors fails with
   `indices: must be unique`.
2. Two identical query rows fail with the same error.

Each check records the command, the actual response, and a verdict. A changed
behavior updates the memo, and the code that relies on it is checked before the
ticket proceeds.

## Glossary

- **baseline**: a JSON record of what a running server answers for a fixed query
  set, used to compare two versions.
- **blocker**: a comparison finding that proves data loss or score drift, and
  that stops the upgrade.
- **Build ID**: the identifier that the compiler writes into a binary, used to
  prove that two binary files are the same build.
- **downgrade**: a move to an older version. Qdrant does not support it, because
  the storage migration is one-way.
- **exact search**: a score computed against every candidate, with no
  approximate index. Its result must not change across an upgrade.
- **HNSW**: the graph index that makes nearest-neighbour search fast and
  approximate.
- **in-place upgrade**: a version change that keeps the existing storage
  directory.
- **minor version**: the second number of a version, for example `20` in
  `1.20.0`.
- **SRI hash**: a checksum written in the `sha256-<base64>` form that Nix uses.
- **storage copy**: a byte copy of the server storage directory, used to test a
  migration without touching the original.
- **warning**: a comparison finding that an upgrade may cause, and that a human
  must read before validation.
