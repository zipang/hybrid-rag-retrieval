# Qdrant review — hybrid index, embedding models, and REST vs gRPC

Ticket: `T0001` — related spec: `roadmap/T0001/spec.md`

This memo records the Qdrant decisions and the measurements for the POC. The
project pins Qdrant `1.19.1`. All behavior below is checked against the local
mirror in `docs/Qdrant - 1.19.1/`.

## 1. The problem this pattern solves

This memo describes a generic retrieval pattern. Use it when the following
conditions hold:

- One text field carries the main meaning of each record. The record is one or
  two sentences long. Call it the **content field**.
- A small set of other fields describe the record. These fields are not part of
  the meaning. They narrow a search. Call them the **filter fields**.
- A user can search in two ways. The user can ask for records with a
  **semantic proximity** to a phrase, or for records with a **syntactic
  proximity** (the exact words). The user can add one or more filter fields.
- The text is international. The records can use accents, and they can use
  more than one language.

The POC applies this pattern to a corpus of advertising slogans. The pattern
also fits other corpora. A good example is a citations dataset:

- content field: the citation text;
- filter fields: the author, the work title, and the publication year;
- a user asks for citations that are close in meaning to a phrase, or for
  citations that contain the exact words, and filters by year or by author.

The rest of this memo uses the citations dataset as the neutral example. The
technology and the measurements do not depend on the dataset.

## 2. Hybrid index approach

The pattern indexes each record as one point in a single collection with **two
named vectors**:

- `dense` — a fixed-dimension vector that represents the meaning of the
  content field. The application computes it with an embedding model.
- `bm25` — a sparse vector with `modifier: "idf"`, generated by Qdrant
  server-side inference (`qdrant/bm25`). It represents the exact words.

Qdrant supports this shape directly. The collection keeps a `vectors` map and a
`sparse_vectors` map. The IDF modifier lets Qdrant compute inverse document
frequency at query time, so the application never computes IDF.

The index also keeps the filter fields in the payload (`author`, `title`,
`year`, and so on). These fields serve as filters only. They do not enter the
vectors.

### Retrieval

One Query API call runs two prefetches and fuses them on the server:

- prefetch 1: the dense query vector as a raw array, `using: "dense"`.
- prefetch 2: `{ text, model: "qdrant/bm25", options }`, `using: "bm25"`.
- main query: `{ "rrf": {} }` (Reciprocal Rank Fusion).

The dense prefetch answers a semantic request. The BM25 prefetch answers a
syntactic request. RRF merges both result lists.

RRF uses ranks, so it does not compare the cosine score against the BM25 score.
The `rrf` object form also accepts `k` and per-prefetch `weights` for later
tuning. Qdrant also offers `dbsf` (score fusion) and weighted RRF. RRF with
default weights is the safe default without an evaluation set.

### Filters

The filter fields apply to the search through the standard filter clause
(`must`, `should`, `must_not`), for example a `range` on the year and a `match`
on the author. The clause accepts one filter or several. This supports the
one/off filter behavior.

Create a payload index for each filter field. An index on a `keyword` field
serves a `match` filter. An index on an `integer` field serves a `match` filter
and a `range` filter. Create the payload indexes **before** the upload. Qdrant
builds filter-aware HNSW edges only for indexes that exist when it builds the
graph. Indexes added later require an expensive graph rebuild.

### BM25 text processing

The BM25 model **defaults to English** stemming and stopwords. For an
international corpus the application must set the `options`:

- `language` — the stemming and stopword language. Choose one language per
  collection, or disable language-specific processing.
- `ascii_folding: true` — `cafe` matches `café`.
- `avg_len` — the average content length in words. The default is `256`. Short
  records need a small value. Without this, BM25 length normalization is wrong.

Qdrant requires the **same options at ingest time and at query time**. The
application reads them from `.env.sample` and builds one shared options object.

For a corpus that mixes languages, or a corpus with names and identifiers,
disable the language-specific steps. Set `stemmer` to `{"type": "none"}`, set
an empty `stopwords` set, and set the `tokenizer` to `multilingual`.

Lowercasing is BM25's default. It is not a configurable BM25 option.

Verified on the running instance: ingest `idées` with the French options, then
query `idées` or `idees` and the point matches. Accent folding works for the
BM25 model, not only for text payload indexes.

### Point identifiers

A Qdrant point id accepts only an unsigned 64-bit integer or a UUID. Choose one
of these two rules:

- the source data already has a numeric key. Map it to the point id, and keep
  the original value in the payload.
- the source data has no numeric key. Generate a UUID, or let Qdrant generate
  one.

The point id must be unique. The payload keeps the display value. The project
types each dataset `id` as an `integer` in its JSON Schema, so the reader
coerces the source text to a number and the importer uses it directly.

### Larger uploads (documented, deferred)

The Qdrant bulk-upload guide describes further options: store dense vectors
on disk for large sets, quantize, move the sparse index to the `cold` tier, and
use 2–4 shards. None of these are necessary for a small or medium corpus.
Extra shards also change IDF statistics, which are computed per shard.

## 3. Embedding model choice

The dense side uses a **local** model by default so the POC runs without an
API key and without network calls at query time.

The `fastembed-js` `3.x` package is the dense embedder. Its only
French-capable dense model is `intfloat/multilingual-e5-large` (1024
dimensions). It has no BM25 model and no `bge-m3`. The model files land in
`local_cache/` (gitignored).

For an international corpus, prefer a **multilingual** model. A model trained on
one language loses quality on another language. Few local multilingual models
exist in `fastembed-js`, so a cloud model can be a better fit for many
languages.

Consequences:

- The first run downloads the model (about 1 GB) and caches it.
- E5 models expect `query:` and `passage:` prefixes. FastEmbed adds them. The
  application should confirm `fastembed-js` does the same, or the dense half
  loses quality.
- `fastembed-js` is dense-only. The sparse BM25 side is fully delegated to
  Qdrant, so the application ships no tokenizer.
- The embedder sits behind a factory (`createEmbedder(env)`), so a cloud model
  (OpenAI, Mistral, Voyage) can replace the local model through `.env` only,
  without changes to the index pipeline.

## 4. REST vs gRPC client

### Documentation

- The Qdrant 1.19 documentation lists only `@qdrant/js-client-rest` for
  JavaScript. It recommends REST for a first use and for a prototype, and
  describes gRPC as a speed option that is harder to debug.
- The bulk-import guide states that gRPC "has lower overhead than HTTP and is
  meaningfully faster for large uploads".
- npm also publishes an official `@qdrant/js-client-grpc@1.19.0` (Connect over
  `node:http2`, gzip by default). It is not in the 1.19 documentation client
  list.

### Benchmark method

Measurement on the local Qdrant `1.19.1`, one collection, one shard, default
settings. Vectors are 1024-dimension dense vectors, batch upload, `wait=false`,
identical data per protocol. Timings stop after `points_count` reaches the
target.

### Results

| Shape | Throughput |
|---|---|
| REST, 1 worker, batch 256 | ~7 000 pts/s |
| REST, 4 workers, batch 256 | ~11 500 pts/s |
| gRPC, 1 worker, batch 256 | ~5 900 pts/s |
| gRPC, 4 workers, batch 256 | ~14 500 pts/s |
| gRPC, 8 workers, batch 256 | ~19 300 pts/s |
| REST, 4 workers, 50k points | 7 449 pts/s |
| gRPC, 4 workers, 50k points | 8 370 pts/s |
| REST, 4 workers, 100k points | 6 035 pts/s |
| gRPC, 4 workers, 100k points | 5 551 pts/s |

REST column-oriented batch and REST record-oriented list performed the same
(about 6 900 pts/s at 1 worker).

### Conclusions

- Single stream, REST is slightly faster and costs one dependency-free `fetch`.
- gRPC scales better at small volume with high concurrency, but the gap closes
  and inverts at large volume. The server is disk-bound once the dataset grows
  and the HNSW optimizer runs.
- The gRPC JavaScript client writes `bigint` point ids and `{ case: ... }`
  wrapper objects. This adds conversion code and a `@bufbuild/protobuf`
  dependency.
- REST serialization of 20,000 points is about 1.6 s in process. The Qdrant
  HTTP request limit is 32 MB by default (about 6,000 points at 1024
  dimensions).

### Recommendation

Keep the **REST client (plain `fetch`)** for the POC. It matches the project
rule of no SDK dependency, it is the documented prototype choice, and it is
faster single-stream and at large volume in this environment. Get throughput
from the documented bulk practices instead of a protocol switch:

1. batch 256 points per request;
2. 2–4 parallel upload workers;
3. create payload indexes before the upload;
4. do not shard a small or medium corpus.

If a later ticket needs maximum ingest speed, add
`@qdrant/js-client-grpc` with 4–8 workers. It is a drop-in change, but it is not
worth the dependency or the boilerplate for this POC.

## 5. Web UI for the bare-metal install

The Qdrant binary release does not include the Web UI. The archive
`qdrant-x86_64-unknown-linux-gnu.tar.gz` for `1.19.1` contains one file,
`qdrant` (30.68 MB). Qdrant serves the browser interface at `/dashboard` only
when a directory named `static/` exists next to the running binary. Without it,
the server logs:

```text
Static content folder for Web UI './static' does not exist
```

and `GET /dashboard` returns `404`. The local mirror documents the Web UI and
the `/dashboard` address in
`docs/Qdrant - 1.19.1/documentation/web-ui/index.md`.

The project needs the Web UI to inspect the collection during the POC. The
project rule excludes Docker, so the setup must install the files. The Qdrant
project publishes the built Web UI in the separate `qdrant-web-ui` repository
(https://github.com/qdrant/qdrant-web-ui/releases). The release asset
`dist-qdrant.zip` holds a `dist/` directory with `index.html`, the `assets/`
directory, and `openapi.json`.

`scripts/setup-qdrant.sh` installs these files. The script downloads the asset
and moves the `dist/` contents into `qdrant/static/`. The script skips the
download when `static/index.html` already exists. Set
`QDRANT_WEB_UI_VERSION` to pin a Web UI release, or leave it at `latest`.

Measurement on the local instance after the install: `GET /dashboard` returns
`200 OK`, and the server log holds no `static content folder` warning.

Related, not chosen: the Docker image bundles the Web UI, and Qdrant Cloud
serves it automatically. Both are outside the project rule for this POC.

## 6. Dense indexing benchmark (local e5-large)

### Method

- Qdrant `1.19.1`, bare-metal, one collection, one shard, default settings.
- Dense model `intfloat/multilingual-e5-large` (1024 dimensions) through
  `fastembed` `3.x` on the CPU (`onnxruntime-node`).
- BM25 side: Qdrant server-side inference. The application ships no tokenizer.
- Client: REST over `fetch`. The importer sends one batch of up to 256 points
  per request with `wait=true`.
- Corpus: `datasets/slogans.txt`, 236 records, about 7 words each.
- Machine: 16 CPU cores, 30.7 GiB RAM.
- Command: `bun run scripts/index-slogans.ts --limit 500`.

The recorded run uses a warm OS page cache. The first cold run took a similar
time.

### Baseline results (`maxLength` 512)

| Metric | Value |
|---|---|
| Records indexed | 236 |
| Rejected blocks | 0 |
| Time to the first log line | 1.6 s |
| Embedding and upload phase | 256.3 s |
| Total wall time | 258.8 s (4 min 19 s) |
| Throughput, total | 0.91 records/s |
| Throughput, embed phase | 0.92 records/s |
| Time per record | 1.10 s |
| Peak resident memory (observed) | about 11 GiB |
| CPU load (observed) | about 1 400 % (about 14 of 16 threads) |

The importer spends almost all of the time in the dense model. Model session
creation is fast (1.6 s). The single `fastembed` call pads each text to the
model `maxLength` of 512 tokens and runs one ONNX inference for the batch. The
upload of 236 points is not measurable next to it.

### Baseline extrapolation

At 0.91 records/s, the full corpus of 265,266 records takes about 81 hours on
this machine. The local CPU model is therefore not practical for the full
corpus. The `--limit` flag keeps the demo run small.

### Padding experiment

Method: embed the first 64 slogans of the corpus (longest record: 12 words)
through the same model with three `maxLength` values. The model session is
created for each value.

| `maxLength` | Time, 64 records | Time per record | Speedup |
|---|---|---|---|
| 512 | 65,868 ms | 1,029 ms | 1.0x |
| 32 | 3,397 ms | 53 ms | 19.4x |
| 16 | 1,656 ms | 26 ms | 39.8x |

The padding to 512 tokens is the main cost. A value of 32 keeps every token of
this corpus and divides the time by about 19.

### Optimized run (`maxLength` 32)

The local embedder now sets the width from `EMBEDDING_MAX_LENGTH` (default 32).
The token counts of the 236 records are min 7, p50 13, p90 18, p99 22, and max
27. A value of 32 keeps every token.

| Metric | Value |
|---|---|
| Records indexed | 236 |
| Rejected blocks | 0 |
| Time to the first log line | 1.7 s |
| Embedding and upload phase | 13.9 s |
| Total wall time | 15.9 s |
| Throughput, total | 14.9 records/s |
| Time per record | 67 ms |
| Speedup, total | 16.3x |

At 14.9 records/s, the full corpus of 265,266 records takes about 5 hours on
this machine, against about 81 hours at the model default. This is practical
for a one-time index.

### Options to raise the throughput

- Use a GPU execution provider for `onnxruntime`.
- Use a cloud embedding provider through the existing embedder factory.
- Add parallel embedding workers. This option helps only when the CPU has idle
  cores. One ONNX inference already uses many threads, so the gain is small
  here.

### Parallelization status

The importer runs one batch at a time. It has no parallel workers. The high CPU
load comes from the `onnxruntime-node` thread pool inside one inference, not
from application concurrency.

## Glossary

- **ANN (Approximate Nearest Neighbor)**: a search that returns near
  neighbors quickly, but not always the exact nearest ones. Qdrant uses it for
  dense vectors.
- **ascii_folding**: a text step that removes diacritics. It turns `é` into
  `e`. A search for `cafe` then matches `café`.
- **BM25**: a keyword ranking function. It scores a record with the frequency
  of the query terms and the rarity of those terms in the collection.
- **content field**: the one text field that carries the meaning of a record,
  for example the citation text or the slogan text.
- **Cosine similarity**: a measure of the angle between two vectors. It shows
  how close two meanings are, independently of vector length.
- **dense vector**: a fixed-length list of numbers that represents the meaning
  of a text.
- **e5**: a family of embedding models, for example
  `intfloat/multilingual-e5-large`. E5 models expect the prefixes `query:` and
  `passage:` on the input text.
- **embedding**: the vector form of a text, an image, or another input. A model
  computes it.
- **fastembed**: a library that runs embedding models locally with ONNX. It
  needs no API key and no network call.
- **filter field**: a payload field that narrows a search, for example the
  year, the author, or the brand. It does not enter the vectors.
- **fusion**: the step that merges the result lists of several retrievals into
  one ranked list.
- **gRPC**: a binary remote procedure call protocol. It uses Protocol Buffers
  and HTTP/2.
- **HNSW**: the graph index that Qdrant uses for fast dense vector search.
- **hybrid search**: a search that combines a dense (semantic) retrieval and a
  sparse (keyword) retrieval.
- **IDF (Inverse Document Frequency)**: a weight that gives rare terms more
  importance than common terms.
- **IDF modifier**: a Qdrant setting on a sparse vector. It lets Qdrant apply
  IDF at query time.
- **inference (server-side)**: a Qdrant feature. Qdrant computes the vector
  from the input text on the server. The project uses it for BM25.
- **payload**: the JSON data that Qdrant stores next to a vector. The project
  keeps the content field and the filter fields there.
- **point**: one record in a Qdrant collection. It holds an id, one or more
  vectors, and an optional payload.
- **prefetch**: a sub-query inside a Query API request. Qdrant runs the
  prefetches first, then applies the main query to their results.
- **quantization**: a compression of vectors into fewer bits. It saves memory
  and can reduce precision.
- **REST**: the HTTP/JSON interface of Qdrant.
- **RRF (Reciprocal Rank Fusion)**: a fusion method based on ranks. A record
  that appears high in several result lists gets a higher score.
- **RSS (Resident Set Size)**: the part of a program's memory that is in RAM.
- **semantic proximity**: a match on the meaning of a text, even with different
  words. The dense vector answers it.
- **shard**: a part of a collection. Each shard has its own write path. The
  project uses one shard.
- **sparse vector**: a vector with few non-zero values. Each non-zero value is
  a `(term, weight)` pair. It represents keywords.
- **static folder**: the directory named `static/` next to the Qdrant binary.
  Qdrant serves the Web UI only when this directory exists.
- **stemming**: a text step that reduces a word to its root. It turns
  `citing` into `cite`.
- **stopword**: a common word that carries little meaning, for example `the` or
  `de`. A search often removes it.
- **syntactic proximity**: a match on the exact words of a text. The BM25
  vector answers it.
- **throughput**: the number of records that a process handles per unit of
  time.
- **vector database**: a database that stores vectors and finds the nearest
  vectors to a query vector.
- **Web UI**: the browser interface that shows the collections and the console.
  Qdrant serves it at `/dashboard`.
- **worker**: one parallel upload stream. The project uses 2 to 4 workers.
